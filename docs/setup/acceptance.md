# Acceptance: evidence, not configuration checkboxes

`iscale setup` distinguishes observed API/data/helper/CLI-screen/store checks from
steps that still need human or external proof. `iscale setup scheduled` records
reported configuration only; it does not certify a scheduler trigger. Browser,
scheduled-run, backup and restore gates stay pending rather than inventing proof.

Before calling your installation complete, keep a private dated evidence folder:

1. Own account approvals and successful US/EU import counts/source dates. Account
   creation, credentials saved and approval emails are reported states, not a DB sync.
2. Private API: unauthenticated request rejected; valid own key returns a real 200
   connected v1 health with fresh nonempty requested registries. Unknown/missing
   registry information is unverified, never complete.
3. Chrome: loaded extension version equals your build; both registry rows agree;
   a known test phrase produces the same result as CLI under identical classes/regions.
   A file manifest alone is not loaded-version proof. Confirm your helper's AI login
   only if using the subscription engine; the CLI agent path needs no AI subscription.
4. Screen one real design/listing, and privately verify CSV import fields/count;
   screen with description coverage and save a risk report. Resolve unverified rows.
5. Observe a **natural scheduler trigger**, process exit codes, latest run time and
   a fresh successful refresh receipt/log. A manual invocation does not prove a trigger.
   Hosted data updates require their own local shop scan proof.
6. Verify a backup's exact bytes/hash and a separate scratch restore with counts and
   known lookups. A TOC listing proves archive readability, not a completed restore.

The release checklist remains closed until a clean installation has real evidence
for its chosen database/platform path. Isolated tests with synthetic data prove
contracts only; they do not replace government approval, a full download, a natural
schedule, the user's account login, or a timed full restore.

## Record your review and continue

Choose `iscale setup workflow cli`, `extension-subscription` or `extension-api`.
The default is CLI; helper/login/extension proof does not block the CLI agent route.
Both fresh extension workflows probe the helper for private trademark-key bootstrap; OpenAI API-key writing has no subscription/login requirement. That bootstrap delivers the machine-local trademark key to the trusted extension independently of the AI provider. An existing stored Chrome key can work without an active helper, but that requires the actual browser acceptance check; CLI agents need neither helper nor extension.

After you personally review a dated proof dossier, use:

```bash
iscale setup review schedule /private/evidence/natural-run.json
iscale setup review extension /private/evidence/browser-check.md
iscale setup review backup /private/evidence/backup-copy.json
iscale setup review restore /private/evidence/scratch-restore.md
iscale setup --json
```

Choose only applicable topics. These commands store the file's hash and classify the
entry as **reported manual review, not independently verified**. They do not parse an
arbitrary file into a successful run or restore. If the file changes/disappears the
record no longer counts as reviewed. `next` progresses the applicable automated
prerequisites; `nextAcceptance` progresses the manual review dossier. The final
message distinguishes observed checks and recorded manual reviews instead of claiming
that an unattended schedule/full restore was proven by a checkbox.
Use dossier files up to 16 MiB, not database dumps or identity documents. In the OpenAI extension workflow, a recorded unchanged browser/key-delivery review makes the bootstrap helper optional; its running/healthy state is still reported separately and no subscription/login claim is inferred.
